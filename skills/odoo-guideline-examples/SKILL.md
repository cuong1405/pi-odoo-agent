# Odoo guideline examples

A guideline says what the rule is; these files show what the rule looks like in real code and
what breaking it looks like. Each example file mirrors one guideline file, section by section,
with blocks copied verbatim from the Odoo source (`crm` first, other modules where `crm` has
no example), each with its path and line range at a pinned commit.

- **Good**: follows the rule. Match its shape.
- **Violation**: real upstream code that breaks the rule, with the fix. Upstream is not
  uniformly compliant (much of it predates the guidelines), so a pattern being common in the
  source never makes it right. Do not copy a violation, and do not extend one because it sits
  next to your change.
- **Observed**: neither clean nor a clear violation; read the note.

The examples do not replace the guideline: open the guideline file whole as well, since an
example shows one case of a rule, not its exceptions. Where an example and a guideline
disagree, the guideline wins and the example is out of date.

## Which file to open

Open the example file of every file type you are about to analyse, write or edit, before you
write it, and again when a check or a review reports a finding about that area.

| File you touch | Example file |
| --- | --- |
| New module, bridge, or deciding where a feature goes | [architecture](examples/examples_architecture.md) |
| Adding or moving files, naming a file or directory | [module structure](examples/examples_module_structure.md) |
| `__manifest__.py` | [manifest](examples/examples_manifest.md) |
| Any Python in an addon: imports, model layout, method names, translated strings | [python](examples/examples_python.md) |
| Domains, computes, constraints, `_order`, state methods, transactions, `create` | [orm](examples/examples_orm.md) |
| Field definitions | [fields](examples/examples_fields.md) |
| `controllers/` | [controllers](examples/examples_controllers.md) |
| `views/`, `data/`, any XML record, view inheritance | [xml](examples/examples_xml.md) |
| Report templates, `_get_report_values` | [reports](examples/examples_reports.md) |
| `security/ir.access.csv`, groups | [security](examples/examples_security.md) |
| ORM calls in loops, `search_fetch`, x2many reads | [performance](examples/examples_performance.md) |
| `tests/` | [tests](examples/examples_tests.md) |
| Comments, docstrings, user-facing strings, commit messages | [comments](examples/examples_comments.md) |
| JavaScript under `static/` | [web javascript](examples/examples_web_javascript.md) |
| Owl templates and icons under `static/` or in views | [web templates](examples/examples_web_templates.md) |
| `*.scss` | [web scss](examples/examples_web_scss.md) |
| Hoot tests and tours under `static/tests/` | [web tests](examples/examples_web_tests.md) |

Not covered: `odoo-security` (audit of `sudo()`, SQL, public methods) and
`odoo-stable-policy`; read those skills directly.

## Provenance

The blocks are generated by `tools/build_guideline_examples.py` of the `pi-setup` repository
from `git show <commit>:<path>` of an Odoo checkout, so a snippet cannot be mistyped. The
curated part is which file and line range shows which rule; line numbers belong to the pinned
commit named at the top of every example file. When the Odoo source or its guidelines move on,
the script is rerun on the new commit after re-checking each range.
